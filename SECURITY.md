# Security Policy

## What this project is

AM64x Secure Boot Studio is a **host-side** toolkit. It prepares, inspects and
verifies secure boot artifacts on a development machine. It does not program
OTP/eFuses, does not perform the HS-FS → HS-SE lifecycle transition, and never
writes to a target device.

Because of that, the security surface is the host tooling itself: how it handles
key material, what it writes to disk, and whether its verification results can be
trusted or misread.

The full claim boundary is documented in
[`docs/SECURITY_BOUNDARY.md`](docs/SECURITY_BOUNDARY.md). Please read it before
reporting an issue — a host-side check passing is *not* a claim that a target
enforces secure boot, and the project states this deliberately.

## Reporting a vulnerability

Please report security issues privately through GitHub's
[private vulnerability reporting](https://github.com/celilaslan/am64x-secure-boot-studio/security/advisories/new)
rather than opening a public issue.

Useful details: affected version or commit, the platform, what you ran, what
happened, and what you expected. **Never include real private keys, MEK values or
other production secrets in a report** — a redacted reproduction is enough.

This is an independent research project maintained by one person, so responses are
best-effort rather than on a guaranteed schedule.

## In scope

Reports that would be treated as security issues:

- **Secret leakage.** A private key path, MEK value, passphrase, key hash or secret
  filename appearing in a report, build record, preferences file, project metadata,
  diagnostics export or artifact index. The project asserts in tests that these do
  not appear; a case that slips through is a bug.
- **Overstated verification.** A host-side result presented as hardware evidence, or
  a check that reports `PASS` when the underlying cryptographic condition does not
  hold — for example a signature, payload hash or certificate/key identity mismatch
  that is not caught.
- **Lifecycle gate bypass.** A path that allows a package built for one lifecycle
  (HS-FS / HS-SE) to be prepared or written for a mismatched board state.
- **Unsafe file handling.** Path traversal, unintended overwrite of a source image,
  or negative-test mutation applied to an original rather than a copy.
- **Unexpected network activity.** The project is offline by design: no telemetry, no
  auto-update, no SDK download. Any outbound connection is a bug.

## Out of scope

- Vulnerabilities in Texas Instruments tooling (`appimage_x509_cert_gen.py`,
  `rom_image_gen.py`), the MCU+ SDK, CCS or UniFlash. Report those to TI.
- Vulnerabilities in third-party dependencies. Report those upstream; if a pin in
  this repository needs bumping, a normal issue or pull request is the right route.
- The deliberate absence of enterprise PKI features (CSR, CA hierarchy, CRL, OCSP).
  These are not part of the version-locked AM64x self-signed flow this project
  implements, and their absence is a documented scope decision.
- The fact that synthetic development keys are non-production. Keys generated by
  `securectl key generate` are explicitly labelled as such and are not intended to
  protect anything.

## Supported versions

The project is in active development at `2.0.0-alpha*`. Fixes land on the default
branch; there are no maintained release branches yet.
